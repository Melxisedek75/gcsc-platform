# XPR Testnet project access and bidding: specification

1. A Contractor with a currently verified XPR Testnet wallet may request a 402 quote for one published, open project. The server, not the client, sets amount, recipient and a memo containing that project ID. A different role, closed project, missing wallet proof, or existing paid entitlement cannot start a new payment.
2. The wallet transaction must come from the bound account and permission on the configured Testnet chain. The server grants the exact `(project, contractor)` entitlement only after verifying the tx hash, recipient, amount, memo, sender, and freshness through Hyperion. A pending or unknown tx never grants access.
3. Replays, retries, concurrent attempts and lost responses cannot spend twice or grant access to another account/project. The phone persists its in-flight transaction before broadcasting and can only recheck the same hash after an uncertain outcome.
4. A confirmed payment and its entitlement are stored atomically in Postgres. The local JSON test mode preserves the same decision rules; it is not production payment storage. If a verified payment arrives after a project closes, record it for manual resolution rather than silently enabling a bid or asking for another payment.
5. The mobile access-required screen displays the exact testnet amount, recipient, job title and project-specific purchase action. It must reload access after server confirmation. The normal bid endpoint remains the final authority; it is not bypassed.
6. Tests cover success and denial paths, wallet mismatch, wrong amount/memo/recipient, duplicate tx, pending verification, storage error, and bid after access. The APK is tested on Pixel 8 without signing until the owner confirms the displayed terms in WebAuth.
7. The server reserves one project/contractor attempt key before issuing a 402 quote. The mobile app durably stores that key before the request and reuses it after quote transport loss. A different device/key is refused. A reservation is not automatically expired because a delayed wallet broadcast could still spend funds; loss of the local journal requires manual chain review before releasing it.
8. A Testnet history node must report the configured Testnet chain ID. Confirmed actions must include the bound sender, permission, recipient, exact amount, exact project memo and valid fresh timestamp. The receipt retains the originally bound permission for later reconciliation even if the app wallet changes.
